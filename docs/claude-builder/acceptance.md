# 卡牌对战游戏 MVP 验收与质量门槛

## 1. 目的

这份文档用于在演示、提交课堂作业或交给下一个开发者前，过滤大部分逻辑错误、代码问题和页面交互问题。

验收原则只有一条：**任何硬门槛失败，当前版本都不能称为完成。**

## 2. 验收顺序

按下面顺序执行，不要只打开网页试玩几下：

1. 安装依赖；
2. 静态检查和语法编译；
3. 自动化测试；
4. Flask 路由与会话测试；
5. 手动完整对局；
6. Git 工作区检查；
7. 记录结果。

## 3. 硬门槛：代码质量

在项目根目录依次运行：

```bash
python -m compileall app.py game
ruff check .
ruff format --check .
pytest -v
```

通过标准：

- `compileall` 没有语法错误；
- `ruff check .` 没有错误；
- `ruff format --check .` 没有格式差异；
- `pytest -v` 的所有测试通过；
- 测试输出中没有跳过的核心规则测试，也没有未处理的 warning 或 traceback。

若 `ruff` 报错，只允许修改被报告的问题并重新运行整套命令；不要为了让检查通过而禁用规则或删除测试。

## 4. 自动化测试覆盖要求

### 4.1 卡牌与角色数据

必须有测试验证：

- 只有战士、法师、游侠三个角色；
- 三个角色的最大生命值分别是 32、24、27；
- 只有五种基础卡牌；
- 固定卡组刚好 12 张，数量为斩击 4、重击 2、护盾 3、治疗 2、火球 1；
- 卡牌消耗与效果数值符合 `docs/mvp.md`。

### 4.2 战斗规则

必须有测试验证：

- 新对局处于 `PLAYER_TURN`，玩家 3 点能量、电脑 28 点生命值、玩家 5 张初始手牌；
- 护盾先吸收伤害，剩余伤害才扣生命值；
- 生命值不为负，治疗不超过最大生命值；
- 成功出牌会扣能量、移出手牌、进入弃牌堆并写入日志；
- 能量不足时，生命值、手牌、弃牌堆、能量和日志都不能变化；
- 不属于玩家手牌的卡不能使用；
- 每回合技能只能使用一次；
- 电脑归零后立刻进入 `VICTORY`，玩家归零后立刻进入 `DEFEAT`；
- 终局后再次出牌、使用技能或结束回合都被拒绝；
- 手牌上限为 6；
- 抽牌堆耗尽时，只在弃牌堆存在时洗回抽牌堆；
- 第 10 回合结束未分胜负时进入 `DRAW`。

### 4.3 电脑 AI 与回合切换

必须有测试验证：

- 电脑生命值小于等于 8 时优先治疗；
- 玩家生命值小于等于 10 时，电脑优先选择当前能量允许的最高伤害牌；
- 电脑生命值小于等于 16 时，在前两项不成立时优先护盾；
- 其他情况下电脑使用最高伤害牌；
- 没有合法卡牌时电脑结束回合；
- 每次玩家结束回合，电脑最多只执行一次动作；
- 电脑行动后，战斗未结束时回合数加 1、玩家能量重置为 3、技能使用标记重置；
- 电脑回合不能被玩家出牌请求改变。

### 4.4 会话、数据库与路由

必须有测试验证：

- `BattleState` 序列化后再还原，状态、手牌、回合数、日志和阶段完全一致；
- 没有进行中的对局时，访问战斗操作会跳转到选角页，不返回 500；
- 选择角色后以 `POST /heroes` 重定向到 `/battle`；
- 使用卡牌、技能和结束回合都使用 POST 后重定向；
- 刷新 `/battle` 只渲染当前状态，不能重复执行上一次动作；
- 对局终局结果只写入 SQLite 一次；
- 重新开始会清除旧对局状态，并回到角色选择页；
- SQLite 数据库文件只保存在 `instance/`，不被 Git 跟踪。

## 5. 代码审查清单

在提交前人工阅读以下内容：

| 检查点 | 必须满足 |
|---|---|
| 规则位置 | 卡牌、伤害、回合和胜负逻辑位于 `game/`，不能写在 HTML 模板或 Flask 路由里 |
| 可变状态 | 不使用模块级全局 `BattleState` 保存不同玩家的对局 |
| 前置校验 | 每个战斗动作先检查阶段、卡牌归属、能量和终局状态，再修改数据 |
| 错误反馈 | 失败操作返回中文明确原因，不吞掉异常或静默失败 |
| 数据库 | SQL 使用参数绑定；数据库连接使用上下文管理器关闭 |
| 会话数据 | Flask session 中只保存 JSON 安全的字典、列表、字符串、数字和布尔值 |
| 路由 | 所有会改变战斗状态的路由是 POST，并遵循 Post/Redirect/Get |
| 模板 | 模板只负责展示与提交表单，不计算伤害、不决定电脑出牌 |
| 范围控制 | 不新增多人、登录、抽卡、商城、外部 AI API 或未批准功能 |

## 6. 手动验收：完整对局

启动应用：

```bash
flask --app app:create_app run --debug
```

按顺序完成以下场景：

| 场景 | 操作 | 预期结果 |
|---|---|---|
| 开始流程 | 打开首页，点击开始游戏 | 进入角色选择页，能看到 3 个角色 |
| 选角保护 | 未选择角色时尝试确认 | 确认按钮不可用或页面给出明确提示 |
| 创建战斗 | 选择任意角色并确认 | 进入战斗页，显示双方生命值、护盾、能量、5 张手牌、回合数和日志 |
| 正常出牌 | 使用一张能量足够的攻击牌 | 能量减少，电脑生命值变化，卡牌离开手牌，日志新增一行 |
| 不足能量 | 将能量用到不足后点击高费用牌 | 卡牌与战斗状态不变化，出现“能量不足”提示 |
| 技能限制 | 使用一次技能后再次点击技能 | 第二次被拒绝，出现“本回合技能已经使用过”提示 |
| 回合交接 | 点击结束回合 | 玩家按钮不可用，电脑只行动一次，然后进入下一玩家回合或结果页 |
| 页面刷新 | 在出牌后的 `/battle` 页面刷新两次 | 生命值、手牌、日志和回合数不额外变化 |
| 终局 | 将一方生命值打到 0 或打满 10 回合 | 进入正确结果页，战斗按钮不再可用 |
| 重新开始 | 点击“再来一局” | 回到选角页，旧手牌、生命值和回合数不被保留 |

检查完后停止本地服务器。

## 7. 交付前 Git 门槛

运行：

```bash
git status --short
git log --oneline --decorate -8
```

通过标准：

- 每个计划任务有对应提交，提交信息与实现内容匹配；
- 不提交 `.venv/`、`__pycache__/`、SQLite 数据库、`.env` 或编辑器缓存；
- 最终工作区没有无意的未跟踪文件；
- README 包含安装、启动、测试和课堂演示步骤。

## 8. Bug 分级和处理

| 级别 | 示例 | 处理要求 |
|---|---|---|
| 阻塞 | 不能开始游戏、出牌后 500、结果错误、刷新重复扣血 | 必须修复并补自动化回归测试，才能交付 |
| 严重 | 能量不足仍能出牌、AI 一回合执行多次、终局还能操作 | 必须修复并补自动化回归测试，才能交付 |
| 一般 | 按钮提示不清楚、日志少了行动方、页面在窄屏溢出 | 修复后重新跑相关测试和手动场景 |
| 轻微 | 文字间距、颜色或卡牌边框不一致 | 可集中修复，但不得影响规则和可读性 |

任何阻塞或严重问题都不能用“课堂作业可以先这样”作为交付理由。
