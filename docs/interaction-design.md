# 卡牌对战游戏：玩法与交互设计

## 1. 设计目标

本文件把 MVP 的“玩家怎么玩、系统如何响应、什么时候结束”固定下来，作为后续 Python 战斗核心和 Flask 页面实现的共同依据。

本版本只追求一件事：玩家能清楚地完成一局战斗，并且每次出牌都能理解结果。

不在本文件中引入登录、多人对战、卡牌收集、复杂 AI 或复杂动画。

## 2. 玩家核心循环

```text
选择角色
  → 双方各自获得英雄、初始手牌和能量
  → 随机决定本局先手
  → 查看双方公开状态
  → 选择卡牌或技能（也可以响应对手的攻击）
  → 看到即时结果和战斗日志
  → 结束回合
  → 对手行动一次
  → 判断胜负
  → 进入下一回合或结果页
```

玩家每回合的核心决策是：

> 在 3 点能量内，决定本回合先攻击、先防守、先治疗，还是保留资源。

玩家和电脑使用完全相同的规则：同一英雄池、每人一副 15 张英雄专属卡组、同样的 3 点能量、6 张手牌上限、护盾累计方式、抽牌与弃牌规则、每回合一次的英雄技能，以及双向的闪避响应。唯一的区别是谁来决策——玩家自己选，电脑由 `game/ai.py` 按难度选。电脑抽到先手时，它开局的整个回合在创建对局时就跑完，玩家只会看到自己的回合或终局。

## 3. 战斗状态机

### 3.1 状态定义

| 状态 | 含义 | 玩家可做的事 |
|---|---|---|
| `START` | 尚未开始 | 点击开始游戏 |
| `HERO_SELECTION` | 正在选择角色 | 查看角色、选择角色、确认角色 |
| `PLAYER_TURN` | 玩家回合 | 出牌、使用技能、结束回合 |
| `ENEMY_TURN` | 电脑回合 | 只能等待，所有玩家操作禁用 |
| `RESPONSE` | 电脑的攻击挂起，等玩家响应 | 使用闪避牌或放弃响应 |
| `VICTORY` | 玩家胜利 | 查看结果、重新开始 |
| `DEFEAT` | 玩家失败 | 查看结果、重新开始 |
| `DRAW` | 达到回合上限，平局 | 查看结果、重新开始 |

### 3.2 合法状态流转

```text
START
  → HERO_SELECTION
  → 由 RNG 随机决定本局先手：
      玩家先手：PLAYER_TURN → ENEMY_TURN → PLAYER_TURN → …
      电脑先手：ENEMY_TURN（创建对局时同步跑完）→ PLAYER_TURN → ENEMY_TURN → …

攻击方打出伤害牌且防御方有可用闪避
  → RESPONSE
  → 攻击方的回合（攻击方是电脑时继续跑完它剩下的行动）

PLAYER_TURN → VICTORY / DEFEAT / DRAW
ENEMY_TURN  → VICTORY / DEFEAT / DRAW / PLAYER_TURN / RESPONSE
RESPONSE    → VICTORY / DEFEAT / DRAW / PLAYER_TURN / ENEMY_TURN
结果状态    → START
```

除上面列出的路径外，其他状态跳转都视为非法。电脑做防御方时响应在结算里当场定夺，不会挂起，所以 `RESPONSE` 只表示“电脑的攻击正等着玩家决定”。

### 3.3 状态保护

每个操作执行前都必须检查当前状态：

- 不是 `PLAYER_TURN` 时，拒绝玩家出牌；
- 不是 `PLAYER_TURN` 时，拒绝玩家使用技能；
- 不是 `PLAYER_TURN` 时，拒绝玩家结束回合；
- 进入 `VICTORY`、`DEFEAT` 或 `DRAW` 后，不再处理战斗操作；
- 页面刷新只重新展示当前状态，不能重复执行上一条操作。

## 4. 战斗初始化

玩家确认角色后，系统创建一份新的 `BattleState`：

- 玩家使用选中的角色，电脑用同一个 RNG 从同一英雄池里随机抽一个，允许和玩家同角色，不做针对玩家的反选；
- 双方最大生命值都取自各自英雄（战士 32、法师 24、游侠 27），当前护盾都是 0，能量都是 3；
- 双方各拿到自己英雄那副 15 张卡组洗牌后的 5 张起手牌，抽牌堆与弃牌堆各自独立；
- 回合数为 1；
- 用同一个 RNG 在玩家与电脑之间公平决定先手；
- 战斗日志写入“战斗开始”和双方选择的角色；
- 电脑先手时，它的整个开局回合在创建流程里同步跑完（包括把开局的响应窗口按放弃结算），接口返回时状态已经是玩家回合或终局。

初始化的这一回合已经抽过 5 张牌，不重复抽牌。之后每个回合开始时，轮到的一方抽 1 张牌。

护盾跨回合保留，不属于“回合开始重置”的资源；双方一视同仁。

## 5. 玩家回合逻辑

### 5.1 回合开始

进入新的 `PLAYER_TURN` 时：

1. 如果不是第 1 回合，玩家抽 1 张牌；
2. 玩家能量重置为 3；
3. 本回合技能使用次数重置为 0，双方各自的长剑加成与铁甲减伤也重置为“本回合还没用过”；
4. 更新页面上的手牌、能量和回合数；
5. 写入“第 N 回合开始”。

手牌上限为 6 张。如果手牌已经达到上限，本次抽牌跳过，并在日志中提示“手牌已满”。

### 5.2 出牌

玩家点击某张卡牌后，系统按下面顺序处理：

1. 检查当前是否为 `PLAYER_TURN`；
2. 检查这张牌是否仍在手牌中；
3. 检查当前能量是否不小于卡牌消耗；
4. 扣除卡牌能量；
5. 执行卡牌效果；
6. 将卡牌从手牌移动到弃牌堆——装备牌例外，它进入自己的装备槽，留在场上而不是进弃牌堆；
7. 写入战斗日志；
8. 判断电脑是否已经生命值归零；
9. 如果没有结束，返回 `PLAYER_TURN`，允许继续操作。

玩家一个回合可以连续使用多张牌，只要能量足够。

### 5.3 特殊技能

每个角色每回合最多使用一次特殊技能。

点击技能按钮后，系统检查：

- 当前是否为 `PLAYER_TURN`；
- 本回合是否已经使用过技能；
- 当前能量是否不小于 2；
- 战斗是否仍在进行。

技能合法时扣除 2 点能量，执行角色技能，写入日志，并把技能标记为“本回合已使用”。

### 5.4 结束回合

玩家点击“结束回合”后：

1. 检查当前是否为 `PLAYER_TURN`；
2. 立即把状态改为 `ENEMY_TURN`；
3. 禁用所有玩家卡牌、技能和结束回合按钮；
4. 显示“电脑行动中”；
5. 电脑按当前能量连续行动，每出一张牌都重新评估一次；
6. 每次行动后判断胜负，出现终局立刻停止；
7. 电脑的攻击如果被玩家的闪避挂起，先停在 `RESPONSE` 等玩家决定，结算完再接着跑完它剩下的行动；
8. 如果战斗没有结束，回到下一个 `PLAYER_TURN`。

“电脑行动一次”指的是电脑的一个完整回合，不是一张牌：它和玩家一样可以在一回合内按能量连出多张牌。

### 5.5 响应攻击

攻击方打出伤害牌时，如果防御方手里有闪避牌并且能量足够，这张牌不会立刻结算，而是挂起并进入 `RESPONSE`：

1. 页面显示进攻牌名称、伤害值和闪避消耗，给出“使用闪避”和“放弃响应”两个选择；显示的伤害是已经算上长剑加成的数值，也就是这一下不闪会实打实落到自己身上的原始伤害；
2. 选择闪避：扣 1 点能量、闪避牌进入弃牌堆，本次伤害完全不结算（铁甲、护盾和生命值都不变，本回合的铁甲也不会因此被用掉）；
3. 选择放弃：按铁甲减伤、再护盾优先的规则正常结算这次伤害；
4. 电脑做防御方时同样有这两个选择，由 `game/ai.py` 按当前难度当场定夺，不阻塞调用方，也不会挂起页面。

响应窗口只处理一次攻击，用完即关；攻击方的费用和弃牌在挂起前就已经结清，响应只决定这次伤害落不落地。

## 6. 卡牌效果

下表的数值对双方完全一致：玩家打出“斩击”打的是电脑，电脑打出“斩击”打的就是玩家。

| 卡牌 | 消耗 | 效果 | 交互反馈 |
|---|---:|---|---|
| 斩击 | 1 | 对敌方造成 6 点伤害 | 对方生命值减少，日志显示伤害 |
| 重击 | 2 | 对敌方造成 10 点伤害 | 对方生命值减少，日志显示伤害 |
| 护盾 | 1 | 自己获得 6 点护盾 | 自己护盾增加，日志显示护盾 |
| 治疗 | 2 | 自己恢复 6 点生命值 | 自己生命值增加，不能超过上限 |
| 火球 | 3 | 对敌方造成 14 点伤害 | 对方生命值减少，日志显示伤害 |
| 闪避 | 1 | 抵消当前这一次攻击 | 只在响应窗口可用，不进入主动出牌候选 |
| 长剑 | 1 | 装备到武器槽，每回合第一次斩击 +2 伤害 | 卡牌离开手牌，进入自己的武器槽，不进取牌堆 |
| 铁甲 | 1 | 装备到护甲槽，每回合第一次受到的伤害 -2 | 卡牌离开手牌，进入自己的护甲槽，不进取牌堆 |

### 6.1 英雄卡组

每个英雄各有一副固定 15 张的卡组，配比不同，所以打法不同；双方各拿自己英雄那一副，抽牌堆与弃牌堆互不影响。

| 英雄 | 卡组 |
|---|---|
| 战士 | 斩击 6、重击 3、护盾 2、治疗 1、闪避 1、长剑 1、铁甲 1 |
| 法师 | 火球 3、重击 3、斩击 4、护盾 2、治疗 1、闪避 1、铁甲 1 |
| 游侠 | 斩击 8、重击 2、护盾 1、治疗 1、闪避 2、长剑 1 |

- 战士的牌最多、护盾和治疗也最多，一局打得更久；
- 法师有 3 张火球，只要能量凑够就能连续打出高价伤害；
- 游侠有 8 张 1 费斩击，配合长剑最容易在一个回合里连打好几张。

同角色对战时双方拿到的是同一副卡组，各自独立洗牌，谁也不比谁多一张。

### 6.2 装备

装备牌和普通手牌一样从牌堆里抽到、花 1 点能量打出，但打出后不进入弃牌堆，而是挂到角色身上——长剑进武器槽，铁甲进护甲槽。装备是**第四个牌区**：任何时刻“手牌 + 抽牌堆 + 弃牌堆 + 装备槽”恒等于整副牌，所以装备牌不会因为被打出而从牌局里消失。

- 每副卡组里同一件装备最多 1 张——长剑进战士和游侠的卡组，铁甲进战士和法师的卡组；装上就一直留着，跨回合保留，本轮没有替换或摘下的规则；
- **长剑只加成斩击**：只有斩击命中时 +2，重击和火球不受影响；
- **铁甲减伤对所有来源生效**：普通攻击牌和英雄的伤害技能都会被减 2；
- 加成和减伤都是**每回合一次**，“用掉”的标记在持有者自己的回合开始时重置，和技能次数同一个生命周期。被护盾完全吸收的伤害同样算用掉了本回合的铁甲；
- 装备只影响持有者的结算，双方的装备各算各的；装了什么是对面也看得见的公开信息。

### 6.3 伤害计算

一次伤害从攻击方算出到防御方扣血，依次经过四步：

```text
基础伤害 = 卡牌或技能的面板伤害
加成后   = 基础伤害 + 长剑加成（只对斩击、且本回合还没触发过）
闪避判定 = 防御方在响应窗口闪避成功则整体归零，后面的步骤都不执行
减伤后   = max(0, 加成后 - 铁甲减伤)（本回合还没触发过铁甲时）
护盾吸收 = min(当前护盾, 减伤后)
生命损失 = 减伤后 - 护盾吸收
```

没有装备时可以等价地看作只走原来的规则：

```text
实际伤害 = max(0, 卡牌伤害 - 当前护盾)
```

当护盾被消耗时，先减少护盾，再减少生命值。生命值不能显示为负数。

### 6.4 非法操作提示

| 场景 | 提示文案 |
|---|---|
| 能量不足 | `能量不足，还差 N 点` |
| 卡牌不在手牌 | `这张卡牌已经不能使用` |
| 电脑回合点击卡牌 | `现在是电脑回合，请等待电脑行动` |
| 技能已用过 | `本回合技能已经使用过` |
| 战斗已结束 | `本局已经结束，请重新开始` |
| 手牌已满 | `手牌已满，本回合没有抽到新牌` |

## 7. 电脑回合逻辑

电脑不使用 `if / elif` 优先级表，也不用 Minimax、MCTS 或深度搜索。每个动作都按同一套流程生成和评估：

1. **生成候选**：手牌中所有费用足够的牌，加上英雄技能（本回合没用过且能量够）和“结束回合”；闪避牌不进入主动候选，只在响应窗口里参加选择。
2. **评分**：攻击牌按实际能打掉的生命（击杀额外加分、溢出伤害不算分、打在护盾上的部分只算削盾价值、并计入能量效率，装上长剑后按加成后的伤害算）；治疗牌只按实际恢复量计分，并随失血比例放大；护盾牌按收益递减计分，同样随失血比例放大；装备牌按它眼下能兑现多少价值定价——长剑看手里还有几张吃加成的斩击（一回合只触发一次，封顶两张），铁甲按 2 点减伤乘以当前失血风险。
3. **选择**：困难模式固定选最高分；中等模式大概率选最高分、偶尔选次优；简单模式在高分候选中更常选到非最优项。所有随机都走可注入的种子随机数，方便复现。留最后 1 点能量给自己手里的闪避算作有正收益的行动，所以中等和困难会主动空过保留响应能力，简单不会。
4. **结算**：由 `BattleState` 统一执行，电脑和玩家共用同一套生命、能量、护盾和抽牌规则。
5. **循环**：每打完一张牌都回到第 1 步，用最新的生命、能量和护盾重新评估，直到没有值得再打的牌就结束回合；因此电脑可以像玩家一样一回合连出多张牌。

### 7.1 电脑能看到什么

电脑每次决策只拿到一份公开信息快照（`AIObservation`）：双方的血量、护盾、能量、英雄、技能是否已用、身上装了什么装备和本回合的装备是否已触发，自己的手牌，公开弃牌记录，公开牌表，以及正在等待响应的那次攻击。玩家的手牌和抽牌堆不在其中，也没有任何字段能反推出它们。

困难模式额外做一步前瞻：如果玩家下回合可能打出的最高伤害足以击杀自己，而当前动作又不能提高生存能力，就对这次行动扣分，让电脑转向治疗或护盾。这个伤害上界只用公开信息估算——公开牌表里买得起的伤害牌取最大值，再加上玩家英雄的伤害技能，再减掉自己身上还没用掉的铁甲；它不知道玩家手里究竟握着哪一张牌，也不拿公开弃牌记录去收窄范围（抽牌堆抽空时弃牌会洗回去，“这张已经打掉了”并不等于它不会回来）。这是一步估算，不做多回合搜索，也不作弊。

电脑每个动作后立刻判断胜负，终局后不再继续出牌。

## 8. 页面交互

### 8.1 开始页

显示：

- 游戏名称；
- 一句话玩法；
- “开始游戏”按钮；
- 简短规则。

交互：

- 点击“开始游戏”进入 `HERO_SELECTION`；
- 不需要注册、登录或输入复杂资料。

### 8.2 角色选择页

显示：

- 三张角色卡片；
- 角色名称、生命值、特点和技能；
- 当前选中的角色。

交互：

- 点击角色卡片后高亮当前选择；
- 没有选择角色时，“确认角色”按钮禁用；
- 点击“确认角色”后创建战斗并进入战斗页。

### 8.2.1 电脑难度选择

- 与角色选择同屏，提供简单、中等、困难三个按钮，默认选中中等；
- 选中项高亮，页面明确写出三档难度使用完全相同的卡牌数值、生命值与能量规则；
- 难度随创建对局的请求一起提交，进入战斗页后显示在电脑名称旁；
- 前端只负责提交和显示难度，不参与任何评分或电脑行动决策。

### 8.3 战斗页

页面分成四个信息区：

1. 电脑状态区：英雄名、生命值、护盾、能量、技能本回合是否已用、当前行动提示；
2. 中央战斗区：回合数、战斗提示和最近一条日志；出现响应窗口时在这里弹出“使用闪避 / 放弃响应”；
3. 玩家状态区：英雄名、生命值、护盾、能量、技能按钮；
4. 手牌区：5–6 张卡牌按钮和卡牌说明。

双方的公开信息对称展示：血量、护盾、能量、英雄、技能状态两边都能看见；手牌保持私有，电脑的手牌在任何页面和接口里都不出现。电脑状态区同时在电脑名称旁显示本局难度，方便人工验收时确认难度已经生效。

按钮状态：

- 能量足够且当前为玩家回合：卡牌按钮可点击；
- 能量不足：卡牌按钮禁用，并显示消耗；
- 电脑回合：所有玩家操作按钮禁用；
- 技能已使用：技能按钮禁用；
- 战斗结束：所有战斗操作禁用，只保留结果入口。

每次成功操作后立即刷新：

- 生命值；
- 护盾；
- 能量；
- 手牌；
- 回合数；
- 战斗日志。

### 8.4 结果页

显示：

- 胜利、失败或平局；
- 使用的角色；
- 总回合数；
- 关键结果，例如造成伤害、剩余生命值；
- “再来一局”按钮。

点击“再来一局”时清空当前战斗状态，回到角色选择页，不沿用上一局的手牌和生命值。

## 9. 后端与前端请求边界

正式前端通过 `/api` 获取 JSON，页面不自行计算伤害、能量、AI 或胜负。接口的完整字段约定见 [docs/api-contract.md](api-contract.md)。

| 请求 | 作用 |
|---|---|
| `GET /api/heroes` | 获取角色目录 |
| `GET /api/cards` | 获取卡牌目录 |
| `POST /api/game` | 使用 `hero_key` 创建战斗 |
| `GET /api/game` | 获取当前公开战斗状态 |
| `POST /api/game/actions/card` | 使用 `card_id` 出牌 |
| `POST /api/game/actions/skill` | 使用角色技能 |
| `POST /api/game/actions/end-turn` | 结束玩家回合并触发一次电脑行动 |
| `POST /api/game/actions/respond` | 对挂起的攻击选择 `dodge` 或 `pass` |
| `POST /api/game/restart` | 清空当前战斗 |

原有 HTML 页面统一放在 `/demo` 下，仅用于本地联调和人工验收；正式页面由后续插件基于 `/api` 重新设计。

## 10. MVP 验收场景

### 场景 A：正常出牌

1. 选择战士；
2. 进入战斗，看到 5 张手牌和 3 点能量；
3. 使用一张斩击；
4. 电脑生命值减少 6，能量减少 1，斩击进入弃牌堆；
5. 战斗日志出现对应记录。

### 场景 B：能量不足

1. 当前只有 1 点能量；
2. 点击火球；
3. 卡牌不从手牌消失；
4. 电脑状态不变化；
5. 页面提示能量不足。

### 场景 C：结束回合

1. 玩家点击结束回合；
2. 页面进入“电脑行动中”；
3. 玩家按钮全部禁用；
4. 电脑按能量连续出牌，直到没有值得再打的牌；
5. 战斗未结束时进入下一次玩家回合。

### 场景 D：战斗结束

1. 玩家造成足够伤害使电脑生命值归零；
2. 页面进入结果页；
3. 所有战斗操作不可用；
4. 点击再来一局后回到角色选择页；
5. 新一局拥有新的手牌、生命值和回合数。

### 场景 E：响应攻击

1. 玩家手里留着闪避牌，点击结束回合；
2. 电脑打出伤害牌，页面弹出响应窗口，显示进攻牌名称、伤害和闪避消耗；
3. 选择“使用闪避”：玩家扣 1 点能量，生命值与护盾都不变，日志出现“抵消了本次伤害”；
4. 选择“放弃响应”：按护盾优先正常扣血；
5. 电脑手里有闪避时，它也会对玩家的攻击做出同样的选择，玩家能在日志里看到结果。

### 场景 F：电脑先手

1. 开一局电脑先手的对局（先手由 RNG 决定）；
2. 创建接口直接返回玩家回合或终局，页面不会停在“电脑行动中”；
3. 战斗日志里能看到电脑开局做了什么；双方能量、护盾、技能状态都能在页面上看到。

## 11. 实现顺序

1. 先实现 `BattleState` 和状态流转；
2. 再实现卡牌效果、能量、护盾和胜负判断；
3. 为核心规则编写自动化测试；
4. 实现电脑的候选生成、效用评分和难度选择 AI；
5. 接入 Flask 路由；
6. 实现四个页面和按钮状态；
7. 最后再做视觉样式、动画和演示优化。
