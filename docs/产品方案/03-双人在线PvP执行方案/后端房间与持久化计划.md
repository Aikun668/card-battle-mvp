# 在线 PvP 后端房间与持久化实施计划

> 上层依据：[产品方向与核心功能](../01-产品方向与核心功能.md)、[在线双人对战架构方案](../02-在线双人对战架构方案.md)。  
> 同级约束：[执行总览与契约门禁](执行总览与契约门禁.md)。正式 HTTP 字段、错误码和时序以 `docs/接口契约/在线PvP/在线PvP接口契约-v1.md` 为唯一事实来源；本文不另行定义或覆盖接口契约。  
> 范围：后端的房间、座位授权、SQLite 持久化、共享 `BattleState`、并发保护与测试实施。不包含页面布局、轮询交互或部署操作。

## 1. 实施目标与不可破坏的边界

目标是在不改变既有人机链路的前提下，使两个独立浏览器能够安全操作同一局 `BattleState`。

- 现有 `POST/GET /api/game`、`game/session_state.py`、`web_support.persist_battle()` 只继续服务人机 Session 对局；在线路由不得读取、写入或清理 `session["battle"]`。
- 在线对局必须使用 `BattleState.create(..., mode="pvp")`、`to_dict()`、`from_dict()` 与 `*_for(side, ...)`；不得复制伤害、回合、响应或胜负规则。
- 在线路由绝不接收 `seat`、`viewer`、`winner`、`battle_state` 等可篡改身份或规则结果的客户端字段；座位只从服务端的凭证解析。
- 对外响应一律由服务端调用 `public_battle_state(battle, viewer=seat)` 生成。数据库中可以保存完整战斗快照，HTTP 响应中不得泄露对手手牌、牌库或弃牌细节。
- 房间流程状态（`WAITING`、`HERO_SELECT`、`PLAYING`、`FINISHED`、`EXPIRED`）与 `BattleState.phase` 分开保存和判断，不能互相替代。

## 3. SQLite 数据模型与约束

`init_db(database_path)` 在原有 `match_results` 之外，以可重复执行的 `CREATE TABLE IF NOT EXISTS` 建立以下表和必要索引。时间均保存为 UTC ISO 8601 文本；JSON 仅保存可由 `BattleState.from_dict()` 还原的数据。

### 3.1 `online_rooms`

| 字段 | 逻辑约束与用途 |
| --- | --- |
| `id` | 内部整数主键；不在邀请链接或 API 中替代公开房间标识。 |
| `room_id` | 随机、不可预测、唯一的公开 UUID/URL 标识；供已授权玩家读取与动作路由使用。 |
| `room_code` | 随机、易输入、唯一的邀请码；只用于加入阶段解析到 `room_id`。 |
| `status` | 仅为 `WAITING`、`HERO_SELECT`、`PLAYING`、`FINISHED`、`EXPIRED` 之一。 |
| `match_number` | 从 1 开始；每次双方确认再来一局递增，用来唯一标识同一房间的某一局。 |
| `revision` | 非负整数；每次改变任何可见房间、座位或战斗状态的成功写入递增。 |
| `battle_state_json` | `NULL` 仅允许在 `WAITING`、`HERO_SELECT`；`PLAYING`、`FINISHED` 必须是完整 `BattleState.to_dict()` JSON。 |
| `result_saved_match_number` | `NULL` 或已写入结果的 `match_number`；同一局只允许从 `NULL` 写为当前局号一次。 |
| `created_at` / `updated_at` / `expires_at` | 房间创建、最后状态变更和过期时刻；所有写入统一更新 `updated_at`。 |

建立 `room_id`、`room_code` 唯一约束与 `expires_at` 查询索引。实现创建时遇到极低概率的唯一冲突，重新生成码后重试，不把内部数据库异常暴露给客户端。

### 3.2 `online_room_players`

一间房始终最多两行，使用 `(room_id, seat)` 主键和座位检查约束；`seat` 只能为 `player` 或 `enemy`。

| 字段 | 逻辑约束与用途 |
| --- | --- |
| `room_id` | 外键关联 `online_rooms.room_id`；删除房间时级联删除座位记录。 |
| `seat` | 创建者固定为 `player`，成功加入者固定为 `enemy`；不能由客户端提交或修改。 |
| `nickname` | 创建/加入时校验后的临时昵称；只作为展示名，不构成授权身份。 |
| `token_hash` | 随机座位凭证的单向摘要；数据库绝不保存原始凭证。 |
| `selected_hero_key` | `NULL` 表示尚未锁定；非空值必须属于现有 `HEROES`。在双方都锁定前，服务层不得向对方公开其值。 |
| `rematch_confirmed_for` | `NULL` 或对应已确认的 `match_number`；防止上局确认在下一局残留。 |
| `joined_at` | 座位创建时间，便于审计与过期诊断。 |

### 3.3 `online_match_results`

结果表与旧 `match_results` 分离，保留对局双方和房间上下文。

| 字段 | 逻辑约束与用途 |
| --- | --- |
| `id` | 内部整数主键。 |
| `room_id` / `match_number` | 联合唯一，确保某房间某一局仅有一条结果。 |
| `player_hero_key` / `enemy_hero_key` | 终局时从完整 `BattleState` 提取的双方英雄。 |
| `winner` | `player`、`enemy` 或 `NULL`（平局）。 |
| `result_reason` | 复用公开结果中的规则结算原因。 |
| `turns` | 终局 `round_number`。 |
| `finished_at` | 服务端写入时间。 |

第一版不记录账号、胜率或排行榜；这张表只用于证明在线对局的结算可追溯，不能反向驱动战斗状态。

## 4. 凭证、会话与授权设计

### 4.1 座位凭证生命周期

1. 创建房间时，服务端生成玩家 1 的高熵随机凭证；只在创建响应中通过 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie（开发测试可按 Flask 测试配置放宽 `Secure`）或现有签名 Session 映射交给创建者。
2. 加入成功时，服务端只为玩家 2 生成另一份凭证。邀请链接只含 `room_code` 或 `room_id`，不含任何座位凭证。
3. 数据库存 `token_hash`，请求到达时以固定实现的摘要函数处理 Cookie 中的原始值，再比对当前房间和座位。原始值不写日志、不放 JSON 响应、不拼入 URL。
4. 浏览器刷新后仍能从自己的 Cookie/签名 Session 恢复座位；复制邀请链接的第三人只能尝试加入，不能获得创建者身份。

推荐将浏览器侧映射限定为“`room_id -> token`”，避免同一浏览器在多个房间互相覆盖。若项目选择 Flask `session` 承载该映射，在线服务仍只接收已解析的原始凭证，不能依赖 `session["battle"]`。

### 4.2 服务层授权顺序

所有查询和动作调用同一入口：`authorize(room_id: str, raw_token: str) -> AuthorizedSeat`。它必须依次完成：房间存在检查 → 惰性过期检查 → 凭证摘要比对 → 返回当前座位与最新房间记录。

- 未携带或无效凭证：按契约返回未授权，不泄露该房间是否有对手、英雄或战斗数据。
- 已授权座位访问过期房间：先把房间原子标为 `EXPIRED`，再按契约返回过期状态；此后不能加入、选英雄、出牌或再来一局。
- 已授权玩家读取房间：可读取同一份公开战场；服务层基于授权座位调用 `public_battle_state`，不接受 HTTP 传来的 `seat` 或 `viewer`。

## 5. `OnlineRoomStore` 的持久化边界

`OnlineRoomStore` 是唯一允许直接读写在线三张表的模块。建议构造为 `OnlineRoomStore(database_path: str, *, now: Callable[[], datetime])`，方便用固定时钟进行过期测试。

它提供以下明确的存储原语；返回不可变记录对象或受控数据传输对象，不把 SQLite row、connection 或 Flask 对象泄露给服务层：

- `create_room(player_nickname, token_hash, expires_at) -> RoomSnapshot`
- `join_waiting_room(room_code, enemy_nickname, token_hash) -> RoomSnapshot`
- `load_authorized_room(room_id, token_hash) -> AuthorizedRoomSnapshot`
- `lock_hero(room_id, seat, hero_key, expected_revision) -> RoomSnapshot`
- `apply_battle_action(room_id, seat, expected_revision, mutate: Callable[[BattleState], ActionResult]) -> ActionOutcome`
- `confirm_rematch(room_id, seat, expected_revision) -> RoomSnapshot`
- `mark_expired_if_due(room_id) -> RoomSnapshot`

`apply_battle_action` 的实现必须在单一 SQLite 写事务（`BEGIN IMMEDIATE`）中完成：读取房间与座位 → 检查未过期、状态为 `PLAYING`、`revision` 相等 → 从 JSON 还原 `BattleState` → 由服务层提供的动作闭包执行 → 把新 JSON 与 `revision = revision + 1` 写回。写入条件必须包含旧 revision；更新行数不是 1 时按契约产生 `STALE_STATE`，并返回可安全展示的最新视图所需记录。

规则拒绝（`ActionResult.ok is False`）不写入战斗快照、不增加 revision；若后端约定在错误响应携带最新状态，则读取当前已保存快照再序列化。这样重复点击、超时重发和另一个请求抢先完成时，都不会从同一旧状态叠加动作。

若动作使 `battle.is_finished()` 成立，`OnlineRoomStore` 在同一事务中完成：房间改为 `FINISHED` → 保存终局 JSON → revision 加一 → 以 `(room_id, match_number)` 联合唯一约束插入 `online_match_results` → 写入 `result_saved_match_number`。唯一冲突必须被视为幂等保护而非第二次结算成功。

## 6. `OnlineBattleService` 的业务边界

`OnlineBattleService` 只编排产品流程，构造为 `OnlineBattleService(store, *, rng_factory, room_ttl)`；`rng_factory` 在测试中可替换为固定种子来源。它不直接写 SQL，也不返回 Flask `Response`。

### 6.1 生命周期方法

| 方法 | 前置条件 | 核心动作 | 结果 |
| --- | --- | --- | --- |
| `create_room(nickname)` | 昵称有效 | 生成房间码和玩家 1 凭证摘要，创建 `WAITING` 房间 | 房间信息、原始凭证（仅供路由写 Cookie）和创建者视角。 |
| `join_room(room_code, nickname)` | 房间仍为 `WAITING` 且第二座位为空 | 原子占用 `enemy` 座位，状态切为 `HERO_SELECT` | 加入者凭证和加入者视角；重复/满房按契约拒绝。 |
| `get_room_state(room_id, raw_token)` | 有效座位凭证 | 授权、惰性过期、根据状态构造视图 | 当前座位视角，盲选时仅含双方 `locked` 布尔状态。 |
| `lock_hero(room_id, raw_token, hero_key, revision)` | `HERO_SELECT`、该座位未锁定、英雄有效 | 原子保存己方选择；若双方均锁定，创建一局 `mode="pvp"` 的 `BattleState` 并转为 `PLAYING` | 最新当前座位视角；双方锁定前不公开英雄。 |
| `play_card` / `use_skill` / `end_turn` / `respond` | `PLAYING`、有效 revision、当前座位拥有对应规则操作权 | 通过 `apply_battle_action` 调用 `BattleState` 的同名 `*_for` 方法 | 动作成功后的当前座位视角，或规则拒绝/版本冲突。 |
| `request_rematch(room_id, raw_token, revision)` | `FINISHED` | 标记当前座位对当前 `match_number` 的确认；两位都确认时清空战斗快照与英雄选择，确认标记清空，`match_number + 1`，状态回到 `HERO_SELECT` | 当前房间视角；单方确认不得重置对手。 |

### 6.2 盲选和对局创建细节

- `lock_hero` 同样使用 `expected_revision`，防止双击锁定或两个浏览器标签页的旧提交覆盖选择。
- 两人都锁定后，在同一个写事务内读取两个英雄，调用 `BattleState.create(player_hero_key, rng, mode="pvp", opponent_hero_key=enemy_hero_key)`，保存 `to_dict()`；不能先分别提交选择、再在事务外创建战斗。
- 创建后只由 `BattleState` 决定先手、初始能量与阶段；在线服务不得额外跑 AI 回合。若先手为 `enemy`，状态应自然保留 `ENEMY_TURN`，等待玩家 2 的设备操作。
- 对局视图构造要将房间元数据与 `public_battle_state` 合并；统一由契约字段规定 `room.status`、`revision`、双方昵称、盲选进度和可操作能力，避免路由各自临时拼字段。

## 7. 过期与再来一局

第一版采用访问时惰性过期，不增加后台常驻调度器。

- `WAITING`、`HERO_SELECT`、`PLAYING`、`FINISHED` 的有效期都由同一明确 TTL 配置产生；具体时长写入接口/部署契约，不能散落在路由常量中。
- 每次创建、加入、锁定、成功动作和成功再来一局确认更新 `updated_at` 并按约定续期；只读轮询不无限续命，避免无人房间永久存在。
- 任何授权读取或写入首先判定 `expires_at`；到期时以条件更新从当前状态改成 `EXPIRED` 并 revision 加一。重复判定必须幂等。
- `EXPIRED` 永不恢复；需要新对局时创建新房间。物理删除是后续运维归档任务，不属于第一版运行路径。

## 8. 测试分组与最小用例

所有在线测试创建两份独立 `FlaskClient`，不得通过手工写同一浏览器 Session 模拟两名真人。除端到端视图外，使用固定 RNG 和可控时钟保证断言稳定。

### 8.1 `tests/test_online_repository.py`

- `init_db` 多次执行仍可用，且旧 `match_results` 测试不受影响；
- 创建房间得到唯一 `room_id`、`room_code`、初始 `WAITING/revision=0` 与一个 `player` 座位；
- 加入只允许一次，两个并发加入尝试最终只有一个获得 `enemy` 座位；
- 相同 revision 的第一个写入成功，第二个写入稳定得到过期版本结果，战斗 JSON 只改变一次；
- 终局触发两次或进程重试时，`online_match_results` 对同一 `(room_id, match_number)` 只有一行；
- 时间推进到 `expires_at` 后首次访问标记 `EXPIRED`，再次访问不再额外增加 revision。

### 8.2 `tests/test_online_service.py`

- 创建者、加入者的凭证只能各自授权对应座位；交换或伪造 token 被拒绝；
- 非法昵称、无效房间码、已满房、已开始房与已过期房按契约状态分类；
- 玩家 1 锁定后，玩家 2 的视图只看到对方已锁定，不能看到英雄 key；双方锁定后才出现完整 PvP `BattleState`；
- 在线服务创建出的战斗保持 `mode="pvp"`，先手为 `enemy` 时不运行 AI；
- 当前回合、响应方和非响应方分别只能调用合法的 `BattleState.*_for` 路径；规则拒绝不增加 revision；
- 终局从 `PLAYING` 仅能转一次 `FINISHED`，双方确认后才清空快照并进入下一局盲选；单方确认不改 `match_number`；
- 人机 `save_battle/load_battle` 与 `persist_battle` 既有行为不依赖在线表。

### 8.3 `tests/test_online_api.py`

- 客户端 A 创建并获得自己的 Cookie，客户端 B 用房间码加入并获得不同 Cookie；两人 GET 同一 `room_id` 看到一致的公开字段和不同的私有手牌；
- 请求中故意附加 `seat=enemy`、`viewer=enemy`，或将动作 JSON 塞入 `seat`，都不能改变服务端识别座位；
- 盲选前、单方锁定后、双方锁定后、自己回合、等对方、自己响应、终局和再来一局均按照正式契约流程串行验证；
- A 出牌后 B 轮询 GET 看见 revision、公开战场和日志更新，但不看见 A 的手牌；
- 使用已缓存 revision 重发动作得到 `409 STALE_STATE`；重新 GET 后只能按最新状态操作；
- 刷新/新建持有同一合法 Cookie 的客户端可以恢复座位；无 Cookie 的第三客户端不能读取战斗；
- 旧 `/api/game` 人机创建、出牌、结束回合、重开和现有热座回归测试照常通过。

### 8.4 `tests/test_online_contract.py`

此文件逐字段镜像 `docs/接口契约/在线PvP/在线PvP接口契约-v1.md`，至少锁定：统一信封、所有成功状态的必有字段、`null` 字段的语义、房间状态枚举、可用操作对象、盲选隐藏字段、Cookie 不进入 JSON、每个错误码的 HTTP 状态、`revision` 类型与递增规则。契约尚未确认前，只创建测试清单；确认后先让测试失败，再开始服务实现。

## 9. 推荐实施顺序与门禁

1. **冻结接口依赖。** 完成并评审 `docs/接口契约/在线PvP/在线PvP接口契约-v1.md`；接口名、信封、错误和 `revision` 语义没有结论前，不创建在线路由。
2. **先写契约与仓储失败测试。** 新建 `test_online_contract.py` 的静态形状测试和 `test_online_repository.py` 的 schema/原子性测试，确认它们因能力缺失而失败。
3. **实现数据库原语。** 扩展 `init_db`，建立在线三表、唯一约束和 `OnlineRoomStore`；先通过仓储测试，再继续上层。
4. **实现纯服务状态机。** 编写 `OnlineBattleService`、凭证摘要、盲选、战斗创建、动作闭包、结果幂等和惰性过期；通过服务测试。
5. **接入 HTTP。** 在 `api_routes.py` 挂载在线路由，将凭证读写限制在路由层，逐个跑契约与双客户端 API 测试；不重构旧 `/api/game`。
6. **完整回归。** 运行 `pytest` 全套，重点核验 `test_api.py`、`test_pvp.py`、`test_session_state.py`、`test_repository.py`；任何人机或冻结热座回归失败都先修复隔离问题，不以改旧契约为代价放行。
7. **交给前端。** 只有在线契约测试、后端双客户端测试和旧模式回归同时通过，才向《前端状态机与对接清单》交付已冻结的接口。

## 10. 后端完成判定

后端阶段可交付的证据必须同时包含：在线契约测试通过、两个独立客户端完整走通创建/加入/盲选/一局战斗/响应/结算/双方再来一局、手牌与座位越权测试通过、旧 revision 与重试不造成双行动、结果表每局一条，以及既有人机与 Session 测试全绿。

只完成路由返回 200、数据库出现一行房间或单浏览器模拟双人，都不构成在线 PvP 后端完成。
