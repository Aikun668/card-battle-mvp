# 在线 PvP 联调验收与部署交付方案

> 上层依据：[执行总览与契约门禁](执行总览与契约门禁.md)。  
> 接口事实来源：[在线PvP接口契约-v1](../../接口契约/在线PvP/在线PvP接口契约-v1.md)。  
> 本文定义交付证据；实际截图、录屏、日志和可再生成报告必须放入 `output/`，人工验收记录放入 `docs/验收/在线PvP/`，不放进本执行目录。

## 1. 验收分层

在线 PvP 的“完成”必须同时具备四类证据，不能只以 HTTP 200、单浏览器演示或页面截图宣称完成：

| 层次 | 要证明的事 | 主要证据 |
|---|---|---|
| 规则与存储 | 房间、身份、盲选、并发与结果存储正确 | 仓储与服务单元测试。 |
| 接口契约 | 文档承诺的字段、错误和隐私边界未走样 | `tests/test_online_contract.py`、双客户端 API 测试。 |
| 前端联调 | 页面只消费冻结协议且能处理等待与错误 | 前端契约测试、浏览器交互检查。 |
| 真实交付 | 两台独立设备在部署域名上完成一局 | 人工验收记录、部署配置检查。 |

## 2. 自动化测试门槛

### 2.1 新增测试分工

| 测试文件 | 最低责任 |
|---|---|
| `tests/test_online_repository.py` | 表结构、唯一约束、revision 比较并交换、惰性过期、结果唯一性。 |
| `tests/test_online_service.py` | 房间状态机、凭证授权、盲选、战斗创建、动作编排、再来一局和 PVE 隔离。 |
| `tests/test_online_contract.py` | RoomSnapshot、字段可空性、错误码、Cookie 不泄露、隐私与版本语义。 |
| `tests/test_online_api.py` | 两个独立 FlaskClient 的创建、加入、轮询、动作、响应、冲突与恢复。 |
| 在线前端契约测试 | 请求不含 `seat/viewer`、revision、状态机、轮询、错误恢复和热座入口冻结。 |

### 2.2 必跑命令

开发阶段按改动范围运行对应测试；交付前必须至少运行：

```text
pytest tests/test_online_repository.py tests/test_online_service.py tests/test_online_contract.py tests/test_online_api.py
pytest
```

若项目已有静态检查命令，也必须在交付记录中注明实际执行结果。测试未执行、环境不具备或真实部署未验证时，必须明确列为“未执行项”，不得以其他测试替代。

## 3. 双客户端 API 集成场景

使用两个互相独立 Cookie 的客户端，依照接口契约逐项走通：

1. A 创建房间，得到 `WAITING`、自己的 Cookie 和邀请信息；
2. B 用房间码加入，双方得到同一房间、不同身份；
3. A 锁英雄，B 只能看到 A 已锁定，不能看到英雄键；
4. B 锁英雄，双方同时进入 `PLAYING`；
5. 验证同 revision 下公开战场一致、`battle.viewer` 不同、只有己方有手牌；
6. 发起至少一轮正常出牌与结束回合；
7. 构造并验证闪避或反制响应只能由真正防守方完成；
8. 使用旧 revision 重发动作，验证仅首次成功，后续稳定得到 `409 STALE_STATE` 和新快照；
9. 走到终局，验证结果仅落库一条；
10. A、B 分别确认再来一局，验证单方不重置、双方确认后返回盲选；
11. 验证无凭证第三客户端、错误房间 ID、过期房间和未知字段均按契约拒绝；
12. 运行既有人机与热座回归测试，确认旧 `/api/game` 不被在线路由影响。

## 4. 浏览器人工验收

真实浏览器验收必须使用两个独立浏览器上下文，例如两部手机、两台电脑，或普通窗口与无痕窗口；不能以同一标签页切座位替代。

| 场景 | 人工预期 |
|---|---|
| 创建与邀请 | 创建者可以复制链接或房间码；加入者打开后进入同一房间。 |
| 等待与盲选 | 创建者能看见加入状态；英雄未双方锁定前互不泄露。 |
| 私有手牌 | 双方同时查看时，只能看到自己的手牌。 |
| 实时性 | 一方结束回合或响应后，另一方在轮询周期内看到正确状态。 |
| 响应 | 攻击方无法替防守方闪避或反制。 |
| 刷新恢复 | 任一玩家刷新后，能恢复原座位和当前局面。 |
| 冲突恢复 | 同一玩家快速重复点击或开双标签操作时，不会双重出牌。 |
| 终局与再来一局 | 双方结果一致；单方确认不清局，双方确认才重新盲选。 |
| 人机回归 | 新入口外，人机模式仍可完整开局、出牌、响应、结算和重开。 |

人工验收至少记录：环境、两个访问端、测试时间、通过/失败、异常现象、未执行项和对应证据路径。记录文件应放入 `docs/验收/在线PvP/<日期>-双端验收.md`；截图或录屏放入 `output/浏览器/在线PvP/<日期>/`。

## 5. 部署验收

公网部署前检查：

- 运行的是长期运行的 Python/Flask 服务，而不是纯静态托管；
- 域名通过 HTTPS 访问，Cookie 的 `Secure` 属性在真实环境生效；
- `SECRET_KEY` 来自部署环境变量，未使用开发默认值；
- Flask 关闭 `debug=True`；
- SQLite 数据库位于平台提供的持久卷，重启服务后房间数据不丢失；
- 第一版只运行一个应用实例，避免 SQLite 跨实例写冲突；
- 服务进程可读写持久卷，但数据库、Cookie、令牌和日志不被公开下载；
- 生产 URL 下两个独立设备已完成第 4 节的真实对局。

课堂演示前，还应准备一次“创建房间 → 手机扫码加入 → 盲选 → 一轮响应 → 终局”的演示路径；若公网环境不可用，应明确记录替代的局域网演示方式，而不是临场修改协议。

## 6. 交付结论格式

最终交付结论必须按下面口径分开陈述：

- **自动化测试**：实际执行的命令、通过数量和失败数量；
- **接口契约**：已锁定的版本、关键隐私与并发用例结果；
- **双端人工结果**：两个独立设备完成到哪一步；
- **部署结果**：域名、HTTPS、持久化与生产配置是否实际验证；
- **未执行项 / 风险**：未验证的部分、原因及其影响。

只有四类证据均满足时，才能宣布“在线 PvP 已交付”。若仅本地双 FlaskClient 或仅单设备通过，应表述为“后端集成通过”或“前端联调通过”，不能表述为公网真人对战已完成。
