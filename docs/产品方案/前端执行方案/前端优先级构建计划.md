# 卡牌对战前端优先级构建计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 在不改变 Flask、接口、战斗规则和固定 1920×1080 舞台的前提下，让前端完整承载当前后端已经公开的战斗状态。

**范围：** 只做前端模板、CSS、轻量 JavaScript 和前端契约测试；后端是唯一规则来源，前端只读取 API 返回的状态并展示。

> **模式边界：** 本计划只维护现有 `/demo` 与本地人机页面。在线 PvP 的创建房间、加入房间和双端对局页面必须按[在线 PvP 前端状态机与对接清单](../03-在线PvP执行方案/前端在线对战状态机与对接清单.md)单独实施，不把热座交接流程重新加入正式入口。

**现状确认（2026-09-24）：** 长剑、铁甲、破甲、蓄力、处决五张素材已存在于 `static/assets/New/`，并且 `static/game.js` 已完成图片映射；卡牌说明已改为读取后端 `card.text`。它们不再是待办。

**依据：** `docs/接口契约/本地对局/api-contract.md`、`game/public_state.py`、`game/catalog.py`。

## 全局约束

- 保持“固定游戏画布 + 整体等比例缩放”：1920×1080、无纵向滚动、比例不变。
- 不修改 Flask、路由、`game/` 规则、AI、接口字段或卡牌数据结构。
- 不在前端重新计算伤害、条件伤害、装备效果、蓄力收益、敌人意图或胜负。
- 继续保留现有背景、角色区、手牌尺寸、卡牌素材、响应面板和扇形手牌交互；只在现有布局内增加紧凑信息槽。
- 所有新增展示必须在字段为 `null`、`0` 或空数组时保持稳定，不出现空白错误或占用大块空间。

## 优先级总览

| 优先级 | 前端内容 | 解决的问题 |
|---|---|---|
| P0 | 动态能量与蓄力结余 | 5 点能量只能画 3 个圆点，玩家不知道下回合攒了多少能量。 |
| P1 | 双方装备槽 | 长剑、铁甲打出后没有落点，持续状态不可见。 |
| P2 | 敌人行动意图 | 后端已有预告，玩家却看不到下一回合风险。 |
| P3 | 消耗牌移除提示与卡牌类型标签 | 处决消失原因不清楚；装备、蓄力都被笼统写成“辅助”。 |
| P4 | 角色选择和结算信息 | 后端已有英雄玩法、牌组摘要和结局原因，页面没有利用。 |
| P5 | 角色头像与最终视觉复核 | 选择法师/游侠时仍是战士头像；统一检查新增区域是否挤压画面。 |

### P0：动态能量与蓄力结余

**读取字段：** `player.energy`、`enemy.energy`、`player.bonus_energy_next_turn`、`enemy.bonus_energy_next_turn`。

**页面位置：** 保持双方现有“护盾 / 能量”这一行；在能量数字旁增加紧凑的“下回合 +N”状态，不新增一整行面板。

- [ ] `renderEnergy()` 根据实际能量渲染圆点，至少支持 `0–5`；能量为 5 时显示 5 个圆点，不能仍固定 3 个。
- [ ] 在双方角色资源区增加“下回合 +N”小标签；值为 `0` 时隐藏。
- [ ] 蓄力打出后，当前能量下降、结余标签出现；下一次自己回合开始后，标签消失且实际能量增加。
- [ ] 为 `0 / 2 / 5` 能量、双方分别蓄力、响应阶段等状态补前端契约测试。

**验收：** 数字、能量圆点和“下回合 +N”不会互相矛盾；不参与能量结算。

### P1：双方装备槽

**读取字段：** `player.equipment.weapon`、`player.equipment.armor`、`enemy.equipment.weapon`、`enemy.equipment.armor`。

**页面位置：** 在上下双方角色信息区各增加一组紧凑的两个槽位：`武器`、`护甲`。空槽仅保留低存在感轮廓；有装备时展示图标、名称和一句短效果。

- [ ] 在模板中增加玩家和电脑各自的装备容器，不改变现有角色区的主列结构。
- [ ] 新建统一的 `renderEquipment(side, equipment)`，只把后端已给出的卡牌定义渲染到对应槽位。
- [ ] 长剑和铁甲使用已有素材；不在前端判断“本回合是否已触发”。
- [ ] 空槽、仅武器、仅护甲、双槽都有装备、双方装备不同的状态都保持对齐。
- [ ] 添加前端契约测试，确认四个槽位和 `state.<side>.equipment` 均被读取。

**验收：** 装备牌从手牌打出后，同一次 API 回包中即出现在正确槽位；双方公开装备信息对称展示。

### P2：敌人行动意图

**读取字段：** `enemy.intent`，字段为 `kind`、`source`、`name`、`value`、`text`；非玩家回合时为 `null`。

**页面位置：** 放在电脑角色区域右端，取代或紧邻现有纯装饰牌堆；它是“下一步预告”，不是一张可点击敌人手牌。

- [ ] 增加紧凑“敌人意图”面板：显示后端 `text`，并按 `kind` 给予攻击 / 防御 / 治疗 / 装备 / 蓄力 / 空过的视觉标签。
- [ ] `intent === null` 时隐藏内容或显示静默占位，不显示过期预告。
- [ ] 文案明确为“预计行动”，避免暗示电脑一定会执行该牌。
- [ ] 为六种 `kind` 和 `null` 写前端契约测试。

**验收：** 玩家回合能看到预告；进入电脑回合、响应阶段和终局后，预告不会残留。

### P3：消耗牌提示与卡牌类型标签

**读取字段：** 手牌/装备的 `effect_type`、`exhaust`、`text`，以及双方 `exhaust_pile`。

**页面位置：** 卡牌底部类型标签继续复用；移除区以双方角色区附近的小计数标识呈现，不新建大型弃牌堆页面。

- [ ] 卡牌类型标签细分为：攻击、防御、治疗、响应、装备、蓄力；不再把装备和蓄力统一写成“辅助”。
- [ ] `exhaust === true` 的卡牌增加“消耗”标记；处决的规则正文继续只读 `card.text`。
- [ ] 双方增加“已移除 N”紧凑计数；当 `exhaust_pile` 非空时可在悬停/预览区显示卡牌名称。
- [ ] 处决打出后，手牌消失、移除计数增加；不能把它渲染成弃牌堆或装备槽。

**验收：** 牌的类别、效果正文和使用后去向一致；前端不凭 key 推断条件伤害数值。

### P4：角色选择与结算信息

**读取字段：** `/api/heroes` 的 `description`、`deck`；对局状态的 `result`（`winner`、`reason`、`text`）。

- [x] 角色选择卡增加一行玩法说明，并简洁显示核心牌组摘要；保持三张角色卡同高，不展开成长表格。
- [x] 结果页优先显示后端 `result.text`，区分击倒、血量结算、护盾结算和平局；字段为空时保留当前兜底文案。
- [x] 为三英雄描述/牌组和四类结局文本写前端契约测试。

**验收：** 玩家在开局前能看懂三个英雄的打法差异；对局结束时能看懂为何胜负。

### P5：角色头像与页面复核

**当前状态（2026-09-24）：** 已补齐法师、游侠正式头像，并完成按 `side + hero.key` 选择头像的前端结构和加载失败兜底。

- [x] 在素材确认后，把玩家头像改为按 `state.player.hero.key` 映射；电脑头像若提供对应素材，同样按 `state.enemy.hero.key` 映射。
- [x] 未提供头像时使用当前可用的通用兜底图，不能产生破图。
- [ ] 用固定 1920×1080 舞台分别验收：空装备、双装备、敌人意图、蓄力 +2、处决已移除、长文案卡牌、三位英雄。
- [ ] 检查没有纵向滚动、右侧不留异常空白、新增信息没有遮住卡牌、技能或响应面板。

**验收：** 法师和游侠不再显示错误的战士身份图；所有 P0–P4 状态在一屏内清楚可读。

## 执行顺序

严格按 `P0 → P1 → P2 → P3 → P4 → P5` 实施。每完成一个优先级，先完成前端契约测试和固定画布截图验收，再进入下一项；不要为了赶进度并行修改多个页面区域。

## 本计划明确不做

- 不新增卡牌、装备、响应链或游戏规则。
- 不修改后端接口、Flask、AI、数值、胜负判定和数据结构。
- 不制作大型牌库/弃牌堆/移除区界面。
- 不重做整体背景、人物区域、手牌尺寸或固定画布缩放逻辑。
