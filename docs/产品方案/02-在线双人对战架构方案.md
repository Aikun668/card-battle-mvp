# 产品方案第二层：在线双人对战架构方案

> 状态：已确认。  
> 前置文档：[第一层：产品方向与核心功能](01-产品方向与核心功能.md)。  
> 范围：定义在线 PvP 的系统边界、状态归属、房间、身份、同步、数据与部署架构；不在本文拆分具体代码任务。

## 1. 架构结论

在线双人对战采用“**房间 + 座位凭证 + 服务端共享对局状态**”架构。

保留现有 `BattleState` 作为唯一战斗规则核心；新增在线房间层负责识别两位玩家、保存共享对局、隔离私有手牌、处理并发请求和管理房间生命周期。

```text
浏览器 A / 浏览器 B
        ↓ 各自的座位凭证
房间 API + 在线对局服务
        ↓ 读取、校验、原子保存
SQLite：房间、座位、对局状态、结果
        ↓
BattleState：现有唯一战斗规则真源
```

在线 PvP 不是另一套战斗规则，而是让两位真人安全地操作同一份 `BattleState`。

## 2. 与现有系统的边界

### 2.1 保留的部分

以下能力继续以现有实现为真源，不因在线化而复制或重写：

- `BattleState` 的回合、卡牌、技能、装备、响应和胜负规则；
- `BattleState.to_dict()` / `from_dict()` 的战斗状态序列化；
- `public_battle_state(battle, viewer)` 的公开状态与手牌视角隔离；
- 人机模式的 AI、难度、意图和现有 `/api/game` 调用链；
- 当前卡牌数值、英雄卡组与平衡口径。

### 2.2 新增的部分

在线 PvP 新增独立的房间域：

- 房间创建、邀请和加入；
- 玩家 1 / 玩家 2 的临时身份与座位凭证；
- 双方盲选英雄；
- 共享对局状态的数据库持久化；
- 版本号并发保护；
- 等待对手时的状态刷新；
- 在线对局结果与双方确认再来一局。

### 2.3 不复用的部分

现有 Flask Session 直接存储 `battle` 的方式只服务人机模式。它代表“此浏览器自己的单人对局”，不能成为两个浏览器共享对局的容器。

原双人热座保持冻结：不作为正式入口，也不作为在线架构的依赖。它已有的双人规则能力可以在规则层继续复用，但交接设备、前端 `seat` 切换和热座遮罩不进入在线流程。

## 3. API 与服务边界

在线 PvP 使用独立命名空间，不修改现有 `/api/game` 的人机语义：

```text
POST /api/rooms                         创建房间
POST /api/rooms/join                    通过房间码加入
GET  /api/rooms/{room_id}               获取当前请求者视角的状态
POST /api/rooms/{room_id}/hero          锁定自己的英雄
POST /api/rooms/{room_id}/actions/card
POST /api/rooms/{room_id}/actions/skill
POST /api/rooms/{room_id}/actions/end-turn
POST /api/rooms/{room_id}/actions/respond
POST /api/rooms/{room_id}/rematch
```

选择独立 API 的原因：

- 人机模式不需要回归到房间、等待对手和身份凭证逻辑；
- 房间状态与单人 Session 不会混在同一条调用链；
- 前端可以清楚地区分“本地人机对局”和“在线共享对局”；
- 冻结的热座接口可在后续单独移除，不阻塞在线模式。

路由只负责解析请求、鉴权和返回响应。房间查询、座位校验、对局加载、规则调用、版本比较和保存集中在在线对局服务中，避免把共享状态编排散落到每个动作路由。

## 4. 房间与座位状态模型

### 4.1 房间状态

每个在线房间处于下列之一：

```text
WAITING       创建成功，等待第二位玩家
HERO_SELECT   两位玩家均已进入，等待双方锁定英雄
PLAYING       正在进行战斗
FINISHED      已结算，允许双方确认再来一局
EXPIRED       已过期，禁止加入与操作
```

房间状态只表达产品流程；战斗回合、响应和胜负仍完全由 `BattleState.phase` 表达。两者不能互相替代。

### 4.2 房间数据

`rooms` 负责保存共享状态，至少包括：

- 内部房间 ID；
- 用于邀请的随机房间码；
- 当前房间状态；
- 对局序号和版本号 `revision`；
- `battle_state_json`（战斗开始后保存 `BattleState.to_dict()`）；
- 创建、更新时间和过期时间；
- 结果是否已持久化的标记。

`room_players` 负责保存两个座位，至少包括：

- 房间 ID；
- 座位（`player` / `enemy`）；
- 临时昵称；
- 座位凭证摘要；
- 已锁定的英雄；
- 是否确认再来一局。

房间码必须随机且不可预测；内部房间 ID 与公开房间码分离，避免把数据库主键暴露为邀请地址。

### 4.3 双方盲选英雄

两位玩家加入房间后各自锁定英雄：

- 玩家只看到“对方是否已锁定”，看不到对方选择的英雄；
- 双方都锁定后，服务端使用两人的选择创建 `BattleState`；
- 创建成功后才对双方公开双方英雄并进入 `PLAYING`；
- 再来一局时重新进入盲选流程。

这避免后进入房间的一方根据先选者的英雄进行反选，保证真人对抗的公平性。

## 5. 身份、授权与隐私

### 5.1 座位凭证

创建者和加入者各自获得一个随机座位凭证。浏览器通过安全 Cookie 或已签名 Session 映射保存自己在某个房间的凭证；数据库只保存凭证摘要，不保存可直接使用的原文。

邀请链接只携带房间码，不携带座位凭证。加入者成功加入后才获得自己的凭证。

### 5.2 服务端决定座位

在线接口不接受客户端传入的 `seat` 或 `viewer` 来决定身份。每个请求都必须经过：

```text
房间 ID
→ 从浏览器凭证识别座位
→ 校验该座位仍属于此房间
→ 服务端确定 viewer
→ 返回该 viewer 的 public_battle_state
```

因此，玩家修改前端请求参数也不能切换到对方座位或读取对方手牌。

### 5.3 信息可见性

双方都可见：

- 双方英雄、生命、护盾、能量和技能状态；
- 装备、蓄力、移除区、反制机会；
- 回合、响应类型、战斗日志和最终结果。

每位玩家只可见：

- 自己当前手牌；
- 自己是否可操作；
- 自己是否需要做响应。

在线服务必须复用 `public_battle_state(battle, viewer)` 输出，禁止前端缓存、推导或请求对手手牌。

## 6. 在线动作与并发保护

每次在线动作遵守同一条服务流程：

```text
鉴权座位
→ 读取房间及 revision
→ 还原 BattleState
→ 校验房间状态与动作合法性
→ 执行 BattleState 规则
→ 共享对局状态与 revision 原子保存
→ 返回当前请求者视角
```

前端提交动作时附带自己看到的 `revision`：

- 版本一致：执行操作，保存后 `revision + 1`；
- 版本过期：返回 `409 STALE_STATE`，前端重新获取房间状态；
- 不属于该座位、未轮到该座位或不在响应方：拒绝操作并返回当前合法状态。

数据库更新需要放在一个写事务中，确保双击、网络重试或双方接近同时请求时，不会从同一份旧状态执行两次操作。

## 7. 状态同步

第一版使用短轮询，不引入 WebSocket。

- 自己的回合：前端可停止轮询或采用低频刷新；
- 等待第二位玩家、等待对手出牌或等待对手响应：每 1–2 秒获取一次房间状态；
- 发现 `revision` 改变时，重绘公开战场、自己的手牌、日志和可用操作；
- 房间进入 `FINISHED` 或 `EXPIRED` 后停止轮询。

在线 PvP 是回合制游戏，短轮询能提供足够自然的体验，并显著降低部署、测试和故障排查成本。

## 8. 结果、再来一局与过期

### 8.1 结果保存

在线对局的结果在房间从 `PLAYING` 转为 `FINISHED` 时由服务端保存一次。保存内容应包含房间、双方英雄、赢家、回合数和结束时间。

不能以“某个浏览器首次看到结果”为保存触发条件，否则双方刷新或轮询会造成重复战绩。

### 8.2 再来一局

再来一局采用双方确认：

```text
任一方点击再来一局
→ 房间记录该方确认
→ 对方确认
→ 清空上局 BattleState 与确认标记
→ 回到 HERO_SELECT
→ 双方重新盲选英雄
```

单方点击不能强制重置另一方正在查看的结果。

### 8.3 房间过期

房间需要具有过期时间，避免数据库累积永不结束的等待房间和中断对局。过期判断和清理策略在第三层执行方案中确定；第一版可采用“访问时惰性判定过期”，不依赖额外的定时任务服务。

## 9. 部署边界

第一版部署形态固定为：一个 Flask 服务实例加一个持久 SQLite 数据库。

它适合课堂演示和少量房间并发，但要求：

- 数据库文件位于部署平台提供的持久磁盘卷；
- `SECRET_KEY` 由部署环境变量提供，不能使用开发默认值；
- 生产环境关闭 Flask `debug=True`；
- 域名通过 HTTPS 反向代理访问该服务；
- 同一阶段只运行一个应用实例，避免 SQLite 多实例写入争用。

如果未来需要更高并发或多实例部署，再将数据库替换为 PostgreSQL；房间 API、在线服务边界和 `BattleState` 规则层不应因此重写。

## 10. 架构验收

第二层完成后，第三层执行方案必须覆盖以下架构验收：

- 人机模式仍由原 Session 对局链路运行，行为不变；
- 两个不同浏览器可以通过同一房间 ID 读取同一局公开战场；
- 任一浏览器无法通过参数伪装或读取对方手牌；
- 英雄在双方都锁定前不泄露；
- 旧 `revision` 的动作不会覆盖已更新的对局；
- 重复动作和网络重试不产生双重出牌；
- 刷新浏览器后，合法玩家可以恢复自己的房间和视角；
- 结果仅保存一次；
- 两人确认后才能开启下一局；
- 过期房间不能被继续加入或操作。
