# 文件组织与归档规范

## 1. 目的与适用范围

本规范约束 `card-battle-mvp` 根目录及其所有子目录中，由开发、测试、设计、部署、工具或自动化新建、下载、生成、移动和归档的文件。目的不是把文件“分得越细越好”，而是让每个文件有唯一且可解释的归属，任何人都能在预期位置找到它。

本规范优先于个人临时习惯。根目录的 [AGENTS.md](../../AGENTS.md) 是执行时的简版强制清单；本文件是判断路径、命名和归档方式的详细依据。

**既有文件保护原则：** 本规范从生效后约束新增和变更。下文对现存文件给出的建议路径仅用于后续整理计划；未获得明确确认前，不移动、删除、重命名或批量重写任何已有文件。

## 2. 全局目录地图

当前项目及后续推荐归属如下：

```text
card-battle-mvp/
├─ app.py / api_routes.py / demo_routes.py / web_support.py  # Web 应用入口与顶层装配
├─ game/                          # 战斗领域规则、状态、存储等 Python 业务代码
├─ templates/                     # Flask 服务的 HTML 模板
├─ static/                        # 浏览器直接使用的 CSS、JS、已确认的游戏静态资源
│  └─ assets/                     # 按资源类型或游戏归属继续分目录
├─ tests/                         # 自动化测试及其明确需要的固定测试夹具
├─ instance/                      # 本机运行时数据，如 SQLite；不得提交真实数据
├─ output/                        # 可再生成的截图、渲染、调试记录、验收产物
├─ docs/                          # 长期保留的说明、决策、契约与验收材料
│  ├─ 产品方案/                   # 产品定位、规则方向、已确认的方案层文档
│  │  ├─ 基础规则/                # MVP 需求、玩法与交互基线
│  │  ├─ 玩法路线/                # 玩法演进、平衡与实验结论
│  │  ├─ 前端执行方案/             # 前端建设与优化计划
│  │  └─ 03-在线PvP执行方案/        # 第三层在线 PvP 的执行拆分文档
│  ├─ 接口契约/                   # 前后端共同遵守、可版本化和可测试的接口契约
│  │  ├─ 本地对局/
│  │  └─ 在线PvP/
│  ├─ 工程规范/                   # 本规范及其他跨项目工程约束
│  │  └─ 工具交接/
│  ├─ 验收/                       # 可追溯的人工验收、发布验收和质量结论
│  │  ├─ MVP/
│  │  └─ 页面视觉验收/             # 页面视觉验收记录
│  └─ 归档/                       # 已替代、已失效但仍需保留的文档
│     ├─ 历史实施计划/
│     ├─ 玩法实验/
│     └─ 旧模式/
├─ requirements.txt / .gitignore / README.md / AGENTS.md
```

目录不是“暂存区”。某个文件不属于上图任何位置时，应先确定它是否真的需要长期存在；需要时先为其建立一个按职责命名的目录和索引，再创建文件。

## 3. 各类文件的唯一放置规则

| 文件类型 | 唯一推荐位置 | 说明 |
| --- | --- | --- |
| Flask 入口、顶层路由装配 | 根目录 | 仅限当前应用明确的启动与装配文件；不得把临时脚本放在根目录。 |
| 战斗规则、领域服务、仓储、序列化 | `game/` 的职责子模块 | 按业务职责命名；不要因为一个新功能随意创建平行的杂项目录。 |
| HTML 模板 | `templates/` | 仅服务端模板；页面私有样式和脚本仍进入 `static/`。 |
| 浏览器 JS、CSS、图片、图标 | `static/` | 静态资源须按资源类型或功能命名，例如 `assets/cards/`、`assets/heroes/`；调试图片不在这里。 |
| 自动化测试与稳定夹具 | `tests/` | 测试文件名与被测能力对应；大体积或可生成资料不作为夹具提交。 |
| 运行时 SQLite、会话或本机数据 | `instance/` | 必须被 `.gitignore` 忽略；不得作为文档、交付物或测试样本散落。 |
| 截图、浏览器录制、渲染、命令日志、临时导出 | `output/<工具或用途>/<功能>/<YYYY-MM-DD>/` | 一律可再生成；必要时在验收文档中引用，不能放入 `docs/` 或源码目录。 |
| 产品定位、机制决策、架构方案 | `docs/产品方案/` | 按主题分目录，方案层文档使用既有 `01`、`02`；当前第三层在线 PvP 执行包使用已确认的 `03-` 前缀。 |
| 某项功能的执行拆分 | `docs/产品方案/03-<功能>执行方案/` | 当前在线 PvP 使用 `03-在线PvP执行方案/`；目录内文件直接表达职责，不再继续追加编号。一个目录只服务一个功能。 |
| 前后端接口契约 | `docs/接口契约/` | 契约是跨前后端的单一事实来源，不混进后端实现计划；名称必须包含接口主题和版本。 |
| 工程规则、协作约定、目录规范 | `docs/工程规范/` | 根目录 `AGENTS.md` 只保留短、可执行的约束，并链接到这里。 |
| 验收记录、上线检查、质量结论 | `docs/验收/<功能或发布批次>/` | 记录测试范围、真实环境结果和未执行项；可再生成附件放 `output/`。 |
| 已替代或停止维护的长期文档 | `docs/归档/<主题>/` | 仅归档文档，不把活跃方案和“也许以后有用”的草稿塞进去。 |

## 4. 新建文件决策表

在任何创建动作前，按以下顺序判断；答案应当唯一落到一个目录。

| 问题 | 是 | 否 |
| --- | --- | --- |
| 它是运行应用必须导入的 Python 源码吗？ | 放到现有入口或 `game/` 对应职责目录。 | 继续判断。 |
| 它是浏览器运行必须加载的页面、样式、脚本或正式素材吗？ | 放 `templates/` 或 `static/`。 | 继续判断。 |
| 它是自动化测试或稳定夹具吗？ | 放 `tests/`。 | 继续判断。 |
| 它是本机运行状态、数据库或密钥派生物吗？ | 放 `instance/` 且确认忽略规则。 | 继续判断。 |
| 它可以通过命令、测试或渲染重新生成吗？ | 放 `output/` 的日期子目录。 | 继续判断。 |
| 它是需要长期维护的产品、接口、工程或验收文档吗？ | 按第 3 节放入对应 `docs/` 主题目录。 | 不创建；先明确用途和保留期限。 |

如果一个文件同时看起来属于两个位置，以“谁消费它、是否需要提交、是否可再生成”决定：应用运行时消费的进源码/静态目录；测试消费的进 `tests/`；人阅读且长期维护的进 `docs/`；可重建的进 `output/`。

## 5. 文档层级与接口契约门禁

`docs/` 根目录不再新增业务文档。新文档必须进入一个已有主题目录，或先建立有明确职责的新主题目录。对在线 PvP，约定如下：

```text
docs/产品方案/
├─ 01-产品方向与核心功能.md             # 已确认的第一层产品基线
├─ 02-在线双人对战架构方案.md             # 已确认的第二层架构基线
└─ 03-在线PvP执行方案/
   ├─ README.md                            # 本执行包范围和依赖索引
   ├─ 执行总览与契约门禁.md
   ├─ 后端房间与持久化实施计划.md
   ├─ 前端在线对战状态机与对接清单.md
   └─ 联调验收与部署交付方案.md

docs/接口契约/
├─ 本地对局/
│  └─ api-contract.md                       # 人机与冻结热座 `/api/game` 契约
└─ 在线PvP/
   └─ 在线PvP接口契约-v1.md                 # 该功能唯一的正式接口事实来源
```

当前已确认第三层在线 PvP 执行包使用 `03-在线PvP执行方案/`，与 `01-产品方向与核心功能.md`、`02-在线双人对战架构方案.md` 对齐。编号只用于执行包目录；执行包内的文件名直接表达职责，不再继续写成 `0301`、`0302`。后续若出现其他第三层功能，必须先确认其编号和主题，再建立独立目录；接口契约仍独立放在 `docs/接口契约/`。

接口契约文件必须包含 URL、方法、请求与响应字段、字段可空性、状态枚举、身份边界、错误码、并发/版本语义和最小调用时序。实现接口、改前端读取字段或增加测试前，先更新契约并完成评审；契约有破坏性变化时新增版本文件，不得悄悄覆写 v1 的含义。

## 6. 命名规则

1. 名称首先表达职责或内容，不表达个人情绪、创建顺序或临时状态。
2. 文档使用清晰中文主题名；需要协议演进时使用稳定版本尾缀，例如 `在线PvP接口契约-v1.md`。日期只用于按时间累积的记录，例如验收、日志和归档索引。
3. 源码和测试沿用项目现有 Python `snake_case`；CSS/JS/静态资源沿用当前 Web 约定，但同一目录内不得混用无意义大小写和中英文临时命名。
4. 临时产物目录使用 `YYYY-MM-DD`；同日多次运行可在其下使用 `HHmmss-用途`。不得用 `final`、`final2`、`最新版` 标记版本。
5. 禁止新建 `New`、`新建文件夹`、`临时`、`测试`、`test`、`misc`、`other`、`final`、`最终版`、`v2最终` 等无法说明归属的文件或目录名。

## 7. 禁止事项

- 禁止在项目根目录新增无启动/配置职责的 Markdown、脚本、截图、数据库、下载文件或导出文件。
- 禁止在 `docs/` 根目录新增产品、接口、前端、测试或计划文档。
- 禁止把执行文档与产品层级文档用连续数字混排，或把不同功能的执行材料放进同一“计划”目录。
- 禁止将截图、HTML 导出、浏览器录像、测试缓存、调试日志放进 `static/`、`templates/`、`game/`、`tests/` 或 `docs/`。
- 禁止以“先放这里，之后再整理”为理由创建未知归属文件；没有明确归属时应先建立方案或不创建。
- 禁止未经确认整理历史文件，包括批量移动、重命名、删除、合并或清空旧目录。
- 禁止把密钥、真实数据库、会话数据和本机配置提交到仓库或作为文档附件保存。

## 8. 归档流程

归档适用于“已被明确替代、已完成且不再维护、或与当前事实冲突但需要保留历史”的文档。按以下步骤执行：

1. 确认替代文件或失效原因，并获得移动授权。
2. 选择 `docs/归档/<主题>/`；按原主题归档，不创建笼统的 `old` 或 `backup` 目录。
3. 文件名保留原可读主题，必要时加日期，不用 `final` 等模糊后缀。
4. 在该主题的归档索引中记录原路径、归档日期、原因和当前替代文件。
5. 更新所有仍指向旧文件的目录索引或链接；检查没有活跃流程仍依赖该文件。
6. 归档后保留 Git 历史，不以删除代替归档；可再生成文件不进入 `docs/归档/`，仍应清理到 `output/` 或不保留。

## 10. 日常检查清单

创建文件前：确认类型、消费者、保留期限和唯一目录。创建后：检查名称是否表达职责、是否污染根目录或 `docs/` 根目录、是否应被 `.gitignore` 忽略、是否需要在主题 README/索引中登记。结构性改动完成后：运行 `git status --short` 和 `git diff --check`，确认没有把无关产物或错误位置的文件带入变更。
