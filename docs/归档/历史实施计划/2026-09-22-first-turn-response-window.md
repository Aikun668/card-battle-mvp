# 电脑先手的响应窗口：不再替玩家做决定（2026-09-22）

## 背景

平衡诊断（见 [英雄平衡落地计划](2026-09-22-hero-balance.md)）的第一步只处理了英雄数值；
对先手优势做定向实验时发现了**一个座位不对称的真问题**：

- 玩家先手时：电脑作为防御方，每次都能正常决策闪避（`choose_enemy_response`）；
- **电脑先手时**：它的整个开局回合在 `BattleState.create()` 里同步跑完，
  期间玩家的每一次响应都被 `while state.phase is RESPONSE: state.respond("pass")`
  **强制放弃**——玩家还没有机会看到棋盘，就被白打了一整个回合的攻击。

实测（镜像，先手胜率）：**电脑先手方向 90.8% vs 玩家先手方向 77.7%**，
相差 13 点；对位读数里也混着这项不对称。

## 预演数据（镜像 300/英雄、对位 400/组，先手对半，HARD）

| 变体 | 镜像先手胜率（enemy 方向） | 对位 战VS法/战VS游/法VS游 |
|---|---|---|
| baseline | 90.8%（85.7 / 98.0 / 88.7） | 41.2 / 48.0 / 41.2 |
| **修强制 pass（定稿）** | **76.1%（70.3 / 84.7 / 73.3）** | **44.0 / 50.7 / 48.0** |
| 修 pass + 先手首回合 2 能量 | 61.0%（53.0 / 58.7 / 71.3） | 40.4 / 49.5 / 36.5 |
| 先手首回合 2 能量（不修 pass） | 75.2% | 38.6 / 43.8 / 31.0 |

**修强制 pass 是纯赚**：两个方向拉平到 76-78%，对位反而全面变好（法VS游 +6.8）。
它与玩家先手方向（77.7%）的差距只剩统计噪声，座位不对称被消除。

## 决策

**`BattleState.create()` 不再替玩家响应：电脑先手时只跑到需要玩家决定的点就返回。**

- `create()` 返回时的 `phase` 现在是三种之一：`PLAYER_TURN`（电脑回合已跑完）、
  `RESPONSE`（有攻击等玩家响应，`pending_attack` 非空）、或终局；
- 调用方（前端）在 `RESPONSE` 时走现有的 `POST /api/game/actions/respond` 端点，
  响应后 `_finish_response()` 会让电脑继续把回合跑完，最终回到 `PLAYER_TURN`；
- demo 页（`static/game.js`）已有完整的响应窗口渲染（`renderResponse`、
  `phaseLabels.RESPONSE`），创建后加载状态即可正确显示，无需新 UI。

### 被否掉的方案（数据在案，留给"先手×英雄联合优化"）

| 方案 | 实测 | 否决理由 |
|---|---|---|
| 先手首回合 2 能量 | 镜像 54.2%（player 方向） | 对位劣化：法VS游 41.2% → 31.0%，破坏英雄平衡 |
| 后手血 +5 | 镜像 48.1%（player 方向） | 对位劣化：战VS法 41.2% → 31.0%，补偿收益按打法分配（速杀型受益最大） |
| 首回合禁攻击 | 镜像 65.4% | 效果不足，且法VS游 41.2% → 32.2% |

三类"先手修正"都对三个英雄的收益不同，必须先做联合微调才能落地。

## 已知遗留

- 修完后先手优势仍有 **76-78%（两方向统一）**：压掉它需要"先手修正 × 英雄数值"
  联合优化（多轮实验），单独立项；
- AI 的防守乘子（失血时过度保守）值约 5 点，排最后。

## 验收记录

真实代码复测（`%TEMP%\first_turn_experiment.py` 的 baseline 组 = 零补丁；镜像 300/英雄、
对位 400/组，先手对半，双方 HARD）：

- **定向**（先手胜率）：电脑先手方向 **76.1%**（战士 70.3% / 法师 84.7% / 游侠 73.3%），
  与玩家先手方向 77.7% 拉平——座位不对称消除；
- **对位**：战VS法 44.0%、战VS游 50.7%、法VS游 48.0%，与预演逐格一致；
- **测试**：267 passed，且连续 **25 轮无 flaky**。顺带修掉三处"本来就存在"的概率性断言：
  创建后状态假设、补牌抽到第二张闪避、电脑开局装铁甲；
- **接口契约**：`POST /api/game` 现在可能返回 `RESPONSE`（`response.active=true`），
  调用方用现有 `respond` 端点继续；demo 页无需改动（响应窗口渲染已就绪）。

先手优势仍有 76-78%（两方向统一）：压掉它需要"先手修正 × 英雄数值"联合优化（限能与
后手补偿都会破坏英雄平衡，数据见上文），单独立项。
